# Validação de API por E2E: passos

## Passos

Passos completos de `.claude/skills/pipeline-maestro/SKILL.md`, seção "Validação de API por E2E", com os nomes completos dos terminais (`[EXECUTOR] <team.roles.executor.tool>` etc.), `<raiz>` o checkout principal e `<gate>` o `node <raiz>/.claude/pipeline/core/pipeline-gate.mjs`.

O critério está em `<knowledge.verification>`, seção "PR de API"; aqui fica a mecânica.

1. Leia `<knowledge.verification>`, seção "PR de API" (oito casos, "não se aplica", formato da linha).
2. Aplique ao PR de API sem tela e à parte de API do PR misto. Sem `team.e2e` → siga o roteiro de portal, registre "E2E de API não configurado" na nota do PR e pare aqui. Detalhe: `.claude/skills/pipeline-maestro/SKILL.md`, seção "Roteamento por tipo de PR". Chaves de E2E: `.claude/pipeline/core/profile-schema.md`, seção "`team`".
3. Prepare o ambiente por `.claude/skills/pipeline-maestro/SKILL.md`, seção "PR aberto pelo executor". Login de `otherRole`, `member` ou `otherTenant` com 401 no primeiro roteiro → rode `<team.dev.seed>`, quando declarado, e redespache antes de reprovar. Detalhe: `.claude/skills/pipeline-maestro/reference/e2e.md`, seção "Usuários do seed".
4. Escreva o cabeçalho com PR, branch, SHA, a seção "Proibições" de `.claude/skills/pipeline-maestro/roles/validador-api.md` copiada literalmente, credencial só pelo nome da variável e o formato da linha da nota do critério.
5. Antes de despachar, rode no Ground `rm -rf <raiz do checkout principal>/.maestri/e2e/pr<pr>` e depois `mkdir -p <raiz do checkout principal>/.maestri/e2e/pr<pr>`; não são linhas do roteiro. A pasta da rodada é `<raiz do checkout principal>/.maestri/e2e/pr<pr>/`. O roteiro não leva `$(…)`, crase, `rm`, `find -delete` nem glob em comando que escreve ou apaga: o Claude Code pede aprovação para eles (`.claude/skills/pipeline-maestro/reference/armadilhas.md`, seção "Terminais e papéis"). Detalhe: `.claude/skills/pipeline-maestro/reference/e2e.md`, seção "Arquivos temporários".
6. Escreva o passo 0 `AMBIENTE`: `curl -sS -o /dev/null -w '%{http_code}' <URL de health>`, 200 esperado; URL = `url` do item de `<team.portals>` cujo `app` é a unidade da API (a skill nunca escreve a URL). Fora de 200 → resposta da seção "Resposta" de `.claude/skills/pipeline-maestro/roles/validador-api.md`, sem reprovar.
7. Escreva login novo por papel de `<team.e2e.users>`, sem reaproveitar jar: `<papel>.cookies` (`-c` no login, `-b` nos passos), `<papel>.login.out`, `<papel>.<nome da credencial>` e, com assinatura, `<papel>.body.json` e `<papel>.headers`, todos dentro da pasta da rodada; `{slug}` vem do papel. Antes do login, uma linha por credencial do papel: `grep '^<VARIAVEL>=' <raiz do checkout principal>/<team.credentials.file> | cut -d= -f2- > <raiz do checkout principal>/.maestri/e2e/pr<pr>/<papel>.<nome>`. O login usa `-H 'Content-Type: application/json'`, um `--variable '<nome>@<arquivo>'` por credencial e `--expand-data '<corpo>'`, em que o corpo é o `<team.e2e.login.body>` em JSON com cada `{<nome>}` trocado por `{{<nome>:trim:json}}` e o `{slug}` resolvido; com `<team.e2e.login.headers>` (cada um como `-H`) e `-c <papel>.cookies`, os `--variable` antes do `--expand-data`; sem `-v`/`--trace`, com `-sS -o <raiz do checkout principal>/.maestri/e2e/pr<pr>/<papel>.login.out -w '%{http_code}'`. Detalhe: `.claude/skills/pipeline-maestro/reference/e2e.md`, seção "Login assinado".
8. Com `<team.e2e.login.signCommand>`, escreva uma linha com `&&`: corpo por `jq -n --rawfile <nome> <arquivo da credencial> …` em `.body.json`, no lugar de `$(…)`, com cada credencial lida por `--rawfile` entrando no corpo como `($<nome> | rtrimstr("\n"))`; assinatura com `{method}`, `{path}`, `{bodyFile}` absoluto, stdout em `.headers`; `curl --data-binary @…body.json -H @…headers`, mais `<team.e2e.login.headers>` e `-c`. Sem `signCommand`, login sem arquivo de corpo nem de cabeçalho. Detalhe: `.claude/skills/pipeline-maestro/reference/e2e.md`, seção "Login assinado".
9. Escreva os passos 1–8, um por caso mínimo do critério: `curl` completo, papel, status e trecho do corpo esperado quando houver. Tire rotas, DTOs, status e mensagens do PR (resumo, `## Decisions`, `## Test plan`) e do module map; recurso criado leva sufixo `e2e-<pr>-<epoch>`, com o epoch literal que o maestro escreve (`date +%s` no Ground, a cada rodada). Detalhe: `.claude/skills/pipeline-maestro/reference/e2e.md`, seção "Nome único por rodada".
10. Escreva os passos 9, 10, …, um por cenário de verificação de API do ticket (marcador de `.claude/pipeline/ticket.md`), inclusive idempotência quando prometida pela rota; o maestro escreve, o validador não acrescenta.
11. Feche o roteiro só com o selo, último passo e só no sucesso: `node <raiz do checkout principal>/.claude/pipeline/core/pipeline-gate.mjs stamp e2e --pr <pr> --sha <sha> --evidence "<…>"`.
12. Envie `maestri ask "[VALIDADOR API] <team.roles.validatorApi.tool>" "<roteiro>"`; nunca cite portal no roteiro.
13. Leia a resposta por `.claude/skills/pipeline-maestro/roles/validador-api.md`, seção "Resposta"; depois de lê-la, seja qual for (`APROVADO`, `REPROVADO`, `AMBIENTE FORA`), rode no Ground `rm -rf <raiz do checkout principal>/.maestri/e2e/pr<pr>`; antes de reprovar por 401/403/429/500 inesperado, confira `.claude/skills/pipeline-maestro/reference/e2e.md`, seção "Armadilhas"; depois `REPROVADO` e `AMBIENTE FORA` seguem `.claude/skills/pipeline-maestro/SKILL.md`, seção "Achado do validador".
14. Com `APROVADO`, confira o log da API na janela da rodada (saída de `<team.dev.up>` no checkout principal), registre a linha "log sem dado pessoal" do critério; `FALHA` → executor como `REPROVADO`.
15. Confira a linha `stamped pipeline/e2e …`; ausente ou de erro → pare: parágrafo **Resposta sem selo.** de `.claude/skills/pipeline-maestro/SKILL.md`, seção "Roteamento por tipo de PR".
16. Não crie arquivo de teste a partir do roteiro; aplique a política de testes de `<knowledge.projectInstructions>`.
